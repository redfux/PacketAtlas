# Architektur – PacketAtlas

## Überblick

PacketAtlas ist eine buildfreie, rein clientseitige Web-App aus nativen ES-Modulen. Es gibt keinen Server-Anteil, keinen Bundler und keinen Build-Schritt – alle Module liegen flach im Projekt-Root (Ausnahmen: `vendor/`, `css/`, `js/`, `icons/`, `docs/`).

```
Datei-Import (app.js)
        │  ArrayBuffer
        ▼
parser.worker.js  ──►  pcap-parser.js / pcapng-parser.js  ──►  packet-decoder.js  ──►  data-model.js (Aggregation)
        │  postMessage: progress / result
        ▼
app.js (UI-Controller)
        │
        ├─► matrix-view.js   (SVG-Adjazenzmatrix)
        ├─► graph-view.js    (SVG + d3-force)
        ├─► export-image.js  (PNG/SVG)
        ├─► export-excel.js  (XLSX via SheetJS)
        └─► pcap-export.worker.js  ──►  pcap-parser.js / pcapng-parser.js / packet-decoder.js / capture-scope.js (PCAP-Export-Fallback für Captures > 1 GiB)
```

## Warum kein Framework

Der Masterprompt fordert eine flache, buildfreie Struktur (GitHub/Gitea-Pages-kompatibel). Ein UI-Framework (React/Vue/…) würde einen Build-Schritt und `node_modules` voraussetzen. Native ES-Module reichen für den Umfang dieser App aus; die Modultrennung (Parser/Datenmodell/Visualisierung/Export) übernimmt dieselbe Aufgabe wie Framework-Komponenten, ohne zusätzliche Abhängigkeit.

## Datenmodell

```js
// Device
{
  id,            // Primärschlüssel: IP-Adresse, oder MAC wenn keine IP bekannt ist
  kind,          // 'ip' | 'mac'
  ip,            // optional
  mac,           // optional (mehrere MACs können auf dieselbe IP zeigen -> letzte gewinnt)
  hostname,      // optional, aus DNS-Antworten
  packetCount,
  byteCount,
}

// Pair (Map<pairKey, Pair>), pairKey = [idA, idB].sort().join('|')
// Seit 2.1.0 nicht mehr vom Worker geliefert, sondern im Main-Thread aus den Verbindungen abgeleitet (derivePairs() in data-model.js).
{
  a, b,                     // Device-IDs (unsortiert original, Anzeige)
  packets, bytes,
  protocols,                 // Set<string>, z. B. {"TCP","UDP","ARP"}
  ports,                      // Set<number>, Vereinigung aus Quell-/Zielports beider Richtungen
  firstSeen, lastSeen,         // Unix-Timestamp (Sekunden, Fließkomma)
  multicastOrBroadcast,        // boolean – für Filter „Multicast/Broadcast ausblenden"
}
```

Die Aggregation läuft während des Parsens **inline** über eine `Map`-Struktur (Schlüssel = sortiertes Geräte-Paar), sodass pro Paket nur ein O(1)-Lookup + Update nötig ist – kein nachträgliches Scannen eines Pakete-Arrays. Einzelpakete werden nach der Aggregation verworfen; der Worker sendet ausschließlich das aggregierte Ergebnis (Device-Liste + Connection-Liste + Statistik) an den Main-Thread zurück; die Paare für Matrix und Graph werden dort aus den Verbindungen abgeleitet (`derivePairs()`). Das hält den Speicherbedarf und die Nachrichtengröße auch bei Captures mit mehreren hunderttausend Paketen klein.

## Parsing-Strategie

### Formaterkennung

Die ersten 4 Bytes des `ArrayBuffer` werden gegen bekannte Magic Numbers geprüft (nicht die Dateiendung):

| Bytes (little/big endian) | Format |
|---|---|
| `A1 B2 C3 D4` / `D4 C3 B2 A1` | klassisches pcap (Mikrosekunden) |
| `A1 B2 3C 4D` / `4D 3C B2 A1` | klassisches pcap (Nanosekunden) |
| `0A 0D 0D 0A` | pcapng (Section Header Block) |

### Klassisches pcap

Globaler Header (24 Byte) liefert Byte-Order, Zeitauflösung und den Link-Layer-Typ (`network`-Feld). Danach folgt eine Sequenz aus Record-Headern (`ts_sec`, `ts_usec`, `incl_len`, `orig_len`) + Payload von je `incl_len` Byte.

### pcapng

Blockbasiertes Format. Relevante Blocktypen:

- **Section Header Block (SHB, `0x0A0D0D0A`)** – enthält das Byte-Order-Magic `0x1A2B3C4D`, mit dem die Endianness der Sektion erkannt wird.
- **Interface Description Block (IDB, `0x00000001`)** – ein Block pro Interface, enthält dessen `LinkType`; wird für spätere Enhanced-Packet-Blocks per Interface-ID nachgeschlagen.
- **Enhanced Packet Block (EPB, `0x00000006`)** – der Regelfall für Paketdaten: Interface-ID, High/Low-Timestamp, Captured/Original Length, Payload.
- **(veraltet) Packet Block (PB, `0x00000002`)** – Fallback für ältere Captures.

Jeder Block trägt seine Gesamtlänge doppelt (Anfang und Ende), was Validierung und robustes Überspringen unbekannter/fehlerhafter Blocktypen erlaubt.

### Warum ein eigener Parser statt einer Bibliothek

Beide Formate sind offen spezifiziert und im hier benötigten Umfang (nur die oben genannten Blocktypen/Records, keine Kommentar-Blocks, keine Namensauflösungs-Blocks etc.) kompakt genug für eine Eigenimplementierung. Das vermeidet Lizenzfragen von Drittbibliotheken, hält den Footprint minimal und erlaubt eine exakt auf die geforderten Layer/Protokolle zugeschnittene Fehlerbehandlung. Für den Force-Directed-Graph wird dagegen bewusst **d3-force** vendort (siehe unten) – ein performanter, interaktiver Kräfte-Simulationsalgorithmus mit Zoom/Pan wäre als Eigenbau unverhältnismäßig aufwändig gegenüber dem Nutzen.

### Link-Layer / L3 / L4

- **Ethernet II** (LinkType 1): 6 Byte Ziel-MAC, 6 Byte Quell-MAC, 2 Byte Ethertype.
- **Linux Cooked Capture / SLL** (LinkType 113): 16-Byte-Header, Protokollfeld an Offset 14.
- **Raw IP** (LinkType 101, außerdem 12/228/229): kein Link-Layer-Header, der Frame beginnt direkt mit dem IP-Header; die IP-Version wird aus dem ersten Nibble gelesen (4 → IPv4, 6 → IPv6). Es gibt keine MAC-Adressen, Geräte werden rein über ihre IP identifiziert. Typisch für Captures auf VPN-/Tunnel-Interfaces.
- **IEEE 802.11 mit Radiotap-Header** (LinkType 127) und **reines IEEE 802.11** (LinkType 105): siehe eigener Abschnitt unten.
- **Ethertype** bestimmt die weitere Verarbeitung: `0x0800` → IPv4, `0x86DD` → IPv6, `0x0806` → ARP.
- **IPv4**: Header-Länge aus IHL, Protokollfeld (TCP=6, UDP=17, ICMP=1) bestimmt L4-Parsing, Quell-/Ziel-Adresse.
- **IPv6**: Fixed Header (40 Byte), Next-Header-Feld (vereinfachte Behandlung, keine vollständige Extension-Header-Kette), Quell-/Ziel-Adresse.
- **ARP**: kein IP-Layer im eigentlichen Sinn, aber Sender-/Target-Protocol-Address (IP) und Sender-/Target-Hardware-Address (MAC) stehen im ARP-Payload und werden für die Geräteerkennung genutzt.
- **TCP/UDP**: erste 4 Byte des Payloads = Quell-/Zielport.
- **ICMP/ICMPv6**: keine Ports, nur als Protokoll-Tag in der Aggregation vermerkt.

### WLAN-Captures (IEEE 802.11 / Radiotap)

Reine WLAN-Mitschnitte (z. B. von Access Points) nutzen üblicherweise LinkType 127 (Radiotap-gekapseltes 802.11) oder seltener 105 (rohes 802.11 ohne Radiotap). Verarbeitung in `packet-decoder.js`:

- **Radiotap-Header** (nur bei LinkType 127): Die Gesamtlänge steht bereits explizit im Header selbst (`it_len`, Offset 2–3, immer Little-Endian). Die einzelnen Radio-Metadaten (Signalstärke, Kanal, Datenrate, …) werden nicht ausgewertet – für die Kommunikationsmatrix genügt es, den Header anhand von `it_len` zu überspringen.
- **802.11-MAC-Header**: Nur **Datenframes** (Type 2) werden weiterverarbeitet; Management-Frames (Beacons, Probe-Requests, …) und Control-Frames (ACK, RTS/CTS) tragen keine IP-Nutzlast und werden ignoriert, ebenso Null-/QoS-Null-Datenframes (Subtype 4/12/14/15), die keinen Frame-Body besitzen.
- **Adress-Interpretation nach ToDS/FromDS-Flags**: Je nach Übertragungsrichtung (Client→AP, AP→Client, IBSS oder WDS mit 4 Adressen) stehen Quell-/Ziel-MAC an unterschiedlichen der bis zu vier Adressfelder. PacketAtlas ordnet die eigentlichen Endgeräte (Stationen) als Kommunikationspartner zu, nicht den Access Point als Relais – die Matrix zeigt also „Client A ↔ Client B", nicht bei jedem Hop „Client ↔ AP".
- **QoS-Control-Feld**: Bei QoS-Datenframes (Subtype ≥ 8) liegen zusätzliche 2 Byte zwischen Adressfeldern/Sequenznummer und der Nutzlast, die entsprechend übersprungen werden.
- **LLC/SNAP-Kapselung**: IP-Verkehr über 802.11 ist praktisch immer per 802.2-LLC/SNAP gekapselt (`AA AA 03` + 3 Byte OUI + 2 Byte Ethertype, RFC 1042). Danach folgt dieselbe IPv4/IPv6/ARP-Verarbeitung wie bei Ethernet. Nicht-SNAP-gekapselte Payloads werden nicht interpretiert.

### DNS-Hostnamen (optional)

`dns-resolver.js` parst zusätzlich Header und erste Frage jeder DNS-Nachricht (`parseDnsMessage()`: ID, Antwort-Flag, Antwortcode, Name); `TrafficStats.addDns()` zählt daraus Anfragen/Antworten, Antwortcodes, fehlgeschlagene Namen, Resolver und Clients mit Fehlern und merkt sich Anfragen (Schlüssel Client|Server|ID, maximal 50.000), deren Antwort nie auftaucht. Hostnamen sind rohe Bytes aus dem Capture und werden deshalb überall, wo sie in `innerHTML` landen, mit `escapeHtml()` (`data-model.js`) escaped. `dns-resolver.js` erkennt UDP-Pakete auf Port 53, parst A-/AAAA-Resource-Records aus DNS-Antworten und baut daraus eine IP→Hostname-Zuordnung, die in Tooltips angezeigt wird, falls vorhanden. Fehlt DNS im Capture, bleibt die Funktion einfach ungenutzt.

### Fehlerbehandlung

Jede Block-/Record-Iteration steht unter Längen-Validierung (Blocklänge/Record-Länge darf nicht über das Ende des Buffers hinausgehen). Bei Inkonsistenzen wird das betroffene Segment übersprungen bzw. das Parsing sauber mit einer verständlichen Fehlermeldung an die UI abgebrochen – kein unbehandelter Exception-Crash.

## Visualisierung

Beide Ansichten rendern **natives SVG** (kein Canvas):

- Vereinfacht den Bild-Export erheblich: SVG lässt sich direkt serialisieren (`.svg`-Download) und für PNG einfach auf einen Offscreen-Canvas zeichnen (`drawImage` + `toBlob`).
- Passt idiomatisch zu d3 (d3-force liefert nur Positionsdaten, d3-selection übernimmt DOM-Bindung).
- Für die Zielszenarien (bis zu einigen hundert Geräten/Kanten) ist SVG-DOM performant genug.

**Matrix** (`matrix-view.js`): SVG-Grid, sequenzielle Farbskala (log-skaliert, da Traffic-Volumen typischerweise stark schief verteilt ist). Der Container ist scrollbar; bei mehr als 50 ausgewählten Geräten weist ein Warnhinweis auf die eingeschränkte Lesbarkeit hin und empfiehlt Filterung (echte sticky Zeilen-/Spaltenköpfe sind für eine spätere Version denkbar, da sie bei reinem SVG-Rendering einen separaten HTML-Overlay erfordern würden). Die linke Zeilen-Beschriftungsbreite, die Höhe der um -45° rotierten Spaltenköpfe sowie ein zusätzlicher rechter Rand werden aus der tatsächlich längsten Geräte-Bezeichnung (bis zu 40 Zeichen) berechnet statt aus einer festen Konstante – eine fixe Höhe/Breite hätte bei langen IPv6-Adressen bzw. IP+Hostname-Kombinationen dazu geführt, dass die diagonale Textausdehnung über den oberen bzw. (bei den letzten Spalten) rechten Rand des SVG-`viewBox` hinausragt und dort abgeschnitten wird – die rotierten Köpfe wachsen bei -45° gleichermaßen nach oben wie nach rechts, weshalb beide Ränder denselben Diagonal-Extent-Wert (`maxLabelLen * CHAR_WIDTH * sin(45°)`) berücksichtigen müssen.

### Direktionale Matrix-Zellen: Verbindungsaufbau vs. Antwort

Ein Geräte-Paar belegt in der Matrix zwei symmetrische Zellen (Zeile A/Spalte B und Zeile B/Spalte A). Da `pair.packets`/`pair.bytes`/`portsA`/`portsB` beide Richtungen zusammen aggregieren, hätten beide Zellen ohne weitere Maßnahme denselben Wert, dieselbe Farbe und dieselben (identischen) Ports angezeigt – unabhängig davon, wie viel Traffic tatsächlich in welche Richtung floss. `derivePairs()` (`data-model.js`) bildet deshalb pro Paar zusätzlich zwei gerichtete Sub-Aggregate `aToB`/`bToA` (aus den Richtungsdaten der Verbindungen) (`packets`, `bytes`, `srcPorts`, `dstPorts`, `firstSeen`, `lastSeen`), befüllt je nachdem, ob das sendende Gerät eines Pakets `pair.a` oder `pair.b` ist. Eine Richtung, die nie Traffic trägt (z. B. eine ARP-Anfrage ohne Antwort oder ein rein einseitiges UDP-Fire-and-forget), wird explizit als Null-Eintrag serialisiert statt `null`, damit `matrix-view.js`/`app.js` nie auf Existenz prüfen müssen.

`matrix-view.js` berechnet Zellfarbe/-wert jeder der beiden Zellen jetzt aus dem zur Zeile passenden Sub-Aggregat (`directionalDataFor()`: Zeile === `pair.a` → `aToB`, sonst `bToA`) statt aus den kombinierten Paar-Werten. Zusätzlich zeichnet jede nicht-leere Zelle einen kleinen, klickunempfindlichen (`pointer-events: none`) Marker: ein gefülltes Dreieck, wenn die Zeile die Verbindung tatsächlich initiiert hat (`pair.a`), ein Ring, wenn die Zeile nur die Antwortrichtung zeigt (`pair.b`) – erkennbar auch ohne Hover, relevant z. B. für Firewall-/ACL-Regeln, bei denen nur die initiierende Richtung eine explizite Freigabe braucht. Eine kurze Legende oberhalb der Matrix (`index.html`) erklärt beide Symbole.

Da die beiden Zellen eines Paares in der Matrix nicht nebeneinander liegen (Zeile A/Spalte B vs. Zeile B/Spalte A, i. d. R. spiegelbildlich um die Diagonale verteilt), ist beim Betrachten einer Zelle nicht auf einen Blick ersichtlich, wo die Gegenrichtung überhaupt sitzt. `renderMatrix()` hält deshalb eine `cellRects`-Map (Schlüssel `"rowId|colId"` → `<rect>`-Element) und hängt an jede Zelle zusätzlich zum bestehenden `mousemove`/`mouseleave` (Tooltip) ein `mouseenter`/`mouseleave`-Paar, das der jeweils anderen Zelle desselben Paares die Klasse `matrix-cell--mirror-hover` hinzufügt bzw. wieder entfernt (gestrichelter Rahmen in Primärfarbe, `style.css`) – Hovern von Zeile A/Spalte B hebt also automatisch auch Zeile B/Spalte A hervor, unabhängig davon, wie weit die beiden Zellen in der Matrix auseinanderliegen.

Tooltip/Kachel für eine Matrixzelle (`matrixCellDetailsHtml()` in `app.js`, getrennt von `pairDetailsHtml()`) zeigt entsprechend „Zeilen-Gerät → Spalten-Gerät" mit den direktionalen Ports/Paketen/Bytes des jeweiligen Sub-Aggregats sowie dem Zusatz „Verbindungsaufbau"/„Antwort". Da zwei Zellen desselben Paares jetzt unterschiedliche Informationen zeigen können, erhält jede beim Anheften eine eigene, zeilen-/spaltenspezifische ID (`pinPair(pair, deviceA, deviceB, directional)` in `app.js`) statt der paar-weiten ID, die der Graph für seine (weiterhin kombinierte, nicht-direktionale) Kanten-Ansicht verwendet – so erzeugt das Anheften beider Zellen eines Paares zwei getrennte Kacheln statt eines No-ops beim zweiten Klick. `exportSelectionToExcel()` (`export-excel.js`) exportiert einen direktional angehefteten Eintrag entsprechend mit einer zusätzlichen Spalte „Richtung" statt der protokollweisen Aufspaltung, die für nicht-direktionale (Graph-)Paare gilt.

### Adressfamilie: getrennte IPv4-/IPv6-/MAC-Ansichten

Matrix und Graph zeigen immer nur **eine** Adressfamilie gleichzeitig – umschaltbar über einen Segmented-Control „IPv4 / IPv6 / Sonstige" in der Toolbar (analog zum Pakete/Bytes-Metrik-Umschalter). Begründung: IPv4- und IPv6-Geräte in derselben Matrix zu mischen ergibt keine sinnvollen Zellen (ein Gerät kommuniziert nie gleichzeitig über beide Familien mit demselben Nachbarn in einem Zellwert), und getrennte Ansichten sind deutlich übersichtlicher als eine gemeinsame, dünn besetzte Matrix. „Sonstige" bündelt Geräte, die nur über ihre MAC-Adresse bekannt sind (z. B. aus nicht-IPv4-ARP) – in der Praxis ein seltener Randfall. Buttons ohne passende Geräte werden deaktiviert; nach dem Parsen wird automatisch die erste nicht-leere Familie (Präferenz IPv4 → IPv6 → Sonstige) vorausgewählt. Die Geräteliste im Seitenpanel bleibt davon unabhängig und zeigt weiterhin alle Geräte aller Familien zur Auswahl an.

Innerhalb der aktuell gewählten Familie werden die Geräte für Matrix-Zeilen/-Spalten und die XLSX-„Matrix"-Tabelle aufsteigend nach Adresse sortiert (`compareDevicesByAddress` in `data-model.js`): IPv4 numerisch pro Oktett, IPv6 numerisch pro Gruppe (mit Expansion der „::"-Kurzschreibweise vor dem Vergleich), MAC-Geräte alphabetisch nach MAC-Adresse. Eine reine String-Sortierung würde bei IP-Adressen falsche Ergebnisse liefern (z. B. „192.168.1.10" vor „192.168.1.5").

**Graph** (`graph-view.js`): d3-force-Simulation (Charge, Link-Distance, Collision), Kantendicke proportional zum gewählten Metrik-Wert, Zoom/Pan über d3-zoom, einstellbare Kräfte-Parameter für Lesbarkeit bei vielen Knoten. Das Layout wird nach jedem Rendern synchron über 300 manuelle `simulation.tick()`-Aufrufe vorkonvergiert und der Viewport per Zoom-to-Fit auf die resultierende Knotenausdehnung angepasst – dadurch ist der Graph sofort vollständig sichtbar, unabhängig davon, ob der rAF-getriebene Simulationstimer im aktuellen Tab-Zustand ungedrosselt läuft.

Beide Ansichten lesen denselben abgeleiteten Zustand aus `data-model.js` (gefilterte Geräteauswahl + gewählte Metrik) und bleiben dadurch synchron.

**Verbindungen** (`connections-view.js`): drittes Tab neben Matrix und Graph, eine korrelierte (nicht-zeitliche) Verbindungsübersicht: pro ausgewähltem Gerät eine senkrechte Lebenslinie mit Kopfbox, pro eindeutiger Kombination aus Geräte-Paar, Protokoll und Port ein waagerechter Pfeil, beschriftet mit Protokoll/Port und Paketanzahl (z. B. „TCP 443 — 25×"), sortiert nach Paketanzahl absteigend (die auffälligsten Verbindungen zuerst). Eine frühere Version zeigte stattdessen einen chronologisch pro Einzelpaket angeordneten Pfeil (echtes Ablauf-/Sequenzdiagramm wie bei Wiresharks „Flow Graph"); auf Nutzerwunsch wurde die zeitliche Anordnung zugunsten dieser korrelierten Übersicht zurückgestellt (siehe [features.md](features.md#backlog-nicht-bestandteil-dieser-version)). Da dies nicht mit der gewählten Metrik (Pakete/Bytes) arbeitet, sondern immer die Paketanzahl je Verbindung zeigt, ist die Metrik-Umschaltung für dieses Tab ausgeblendet. Um die Lesbarkeit auch bei sehr vielen unterschiedlichen Verbindungen zu begrenzen, werden höchstens `MAX_CONNECTIONS_RENDER` (400) Verbindungen gleichzeitig gezeichnet; wird diese Grenze überschritten, erscheint ein Warnhinweis mit der Empfehlung, weiter zu filtern.

Wie ein Geräte-Paar in der Matrix aggregiert eine Connection ursprünglich beide Richtungen in einer einzigen Summe (`connection.packets`/`bytes`), was die Antwortrichtung eines Request/Response-Austauschs (z. B. die TCP-Antwortpakete eines Servers) komplett unsichtbar machte. `parser.worker.js` hält deshalb zusätzlich zwei direktionale Sub-Aggregate `aToB`/`bToA` (`packets`, `bytes`, `srcPort`, `dstPort`, `firstSeen`, `lastSeen` – ein einzelner repräsentativer Port genügt hier, da eine Connection bereits auf einen Service-Port eingegrenzt ist, anders als bei Pair-Ports über ein ganzes Geräte-Paar hinweg). `connections-view.js` baut daraus über `directionView()` zwei „Connection-förmige" Sichten (Initiator: `aToB`, Antwort: `bToA`, mit vertauschtem `a`/`b`/`srcPort`/`dstPort`), die unverändert in `connectionDetailsHtml()`/`pinConnection()` (`app.js`) weiterverarbeitet werden können, ohne dort etwas ändern zu müssen. Existiert Antwort-Traffic (`bToA.packets > 0`), zeichnet die Ansicht beide Pfeile eng untereinander (18px Abstand statt der sonst 34px Zeilenhöhe) mit einem gemeinsamen, leicht hinterlegten Rundrechteck-Band, damit optisch klar erkennbar ist, welche zwei Pfeile zusammengehören; der Antwort-Pfeil ist gestrichelt/gedimmt und trägt ein „○"-Präfix im Label (Initiator: „▲"), konsistent zur Matrix-Legende. Das Label zeigt den Destination-Port der jeweiligen Richtung (`connectionLabel()`), nicht den beiden Pfeilen gemeinsamen Service-Port (`connection.port`) – welche beiden Ports insgesamt beteiligt sind, ergibt sich bereits aus den zwei gruppierten Pfeilen, der volle Source-/Destination-Port-Umfang bleibt im Hover-Tooltip (`connectionDetailsHtml()`) verfügbar. Bei ICMP/ICMPv6 (kein Port vorhanden) zeigt das Label stattdessen den tatsächlichen Nachrichtentyp der Richtung, z. B. „ICMP (Echo Request)" / „ICMP (Echo Reply)" statt nur „ICMP" – dafür trackt `parser.worker.js` pro Connection-Richtung zusätzlich ein `icmpTypes`-Set (aus dem ersten Byte des ICMP-Headers, `decoded.icmpType` in `packet-decoder.js`), und `icmpTypeLabel()` in `data-model.js` bildet die IANA-Typnummern (RFC 792/4443, gängige Teilmenge) auf lesbare Namen ab, mit Fallback „Typ N" für Unbekanntes. ARP-Request/-Reply werden bewusst nicht unterschieden (nicht angefragt, und ARP transportiert ohnehin keine vergleichbare Typinformation im selben Sinne). Eine reine Einweg-Connection (z. B. eine unbeantwortete ARP-Anfrage) zeichnet weiterhin nur den einen Pfeil. Da Initiator- und Antwort-Sicht dieselbe `pairKey`-sortierte ID erzeugen würden, verwendet `connectionId()` in `app.js` bewusst die ungeordnete `a->b`-Reihenfolge, damit sich beide Pfeile unabhängig anheften lassen.

Bei vielen ausgewählten Geräten wird das eigentliche Diagramm (feste Lebenslinien-Abstände × Zeilenhöhe pro Verbindung) schnell deutlich größer als der sichtbare Ansichtsbereich. Analog zum Graphen wird das SVG-Element selbst auf die Containergröße gesetzt und der Diagramminhalt in einer Zoom-Layer-Gruppe untergebracht, die per `d3.zoom()` initial per Zoom-to-Fit auf die volle Diagrammausdehnung skaliert wird (Faktor ≤ 1, nie vergrößert) – ohne diesen Schritt wäre beim Öffnen des Tabs oft nur ein leerer Ausschnitt zu sehen. Zoom/Pan bleiben danach interaktiv nutzbar, um Details bei vielen Geräten/Verbindungen zu untersuchen.

Der Worker aggregiert die Verbindungen **vollständig und unbegrenzt**, genau wie die Geräte-Paare – anders als ein Log einzelner Pakete braucht diese Aggregation keine Obergrenze, da pro Paket nur ein O(1)-Map-Lookup auf den Schlüssel `Geräte-Paar|Protokoll|Service-Port` anfällt (`Aggregator.connections` in `parser.worker.js`). Der „Service-Port" einer Verbindung ist der kleinere der beiden beteiligten Portnummern (`servicePortOf()`) – ein einfacher, aber in der Praxis fast immer zutreffender Kniff, um Client-seitige, wechselnde Ephemeral-Ports und Server-Port in einer Zeile zusammenzuführen, statt für jede neue Client-Verbindung eine eigene Zeile zu erzeugen.

**Statistik** (`stats-view.js`, Daten aus `traffic-stats.js`): fünftes Tab, capture-weite Kennzahlen statt gefilterter Geräte-/Paar-Sicht. `traffic-stats.js` ist eine zweite Akkumulator-Klasse (`TrafficStats`) im Parse-Worker neben dem `Aggregator`: jedes dekodierte Frame wird zusätzlich dort verbucht (Protokoll-/Cast-/IP-Version-Zähler, Größen-Buckets, Pakete pro Sekunde, Ports, ICMP-Typen, TCP-Flags) und liefert am Ende ein einziges, schlankes `stats`-Objekt in der Result-Nachricht. Die TCP-Analyse hält pro Stream und Richtung nur wenige Zahlen (nächste erwartete Sequenznummer, letzter ACK/Window, Dup-ACK-Zähler) und erkennt nach Wiresharks Heuristik: Retransmission (Sequenznummer unterhalb der erwarteten, später als 3 ms nach dem Original), Out-of-Order (innerhalb von 3 ms), Lücke (Sequenznummer springt nach vorn), Dup-ACK (identischer ACK/Window bei noch offenen Daten der Gegenseite), Fast Retransmit (Retransmit nach ≥ 3 Dup-ACKs auf genau diese Sequenznummer), Keep-Alive, Zero-Window und RST; Sequenzvergleiche laufen mit 32-Bit-Überlauf (`(a - b) | 0`). Das ist eine reine Heuristik – bei Captures, die mitten in einer Verbindung beginnen, oder wenn der Messpunkt abseits des Verlusts liegt, kann sie abweichen. Dieselben TCP-Ereignisse werden außerdem pro Paket aus `TrafficStats.add()` zurückgegeben und vom `Aggregator` (`parser.worker.js`, `addPacket(decoded, tcpEvents)`) den Paaren, Verbindungen und Richtungen zugeordnet: `problems` (Anzahl Retransmits + Lücken + RST + Zero-Window + ICMP-Fehlermeldungen; Dup-ACKs/Out-of-Order zählen bewusst nicht mit, da sie dieselbe Ursache doppelt zählen würden) sowie ein `tcp`-Summary (Zähler, Handshake-Zeiten, FIN/RST, bei Verbindungen zusätzlich bis zu 200 Problem-Zeitstempel für die Mini-Zeitleiste). `healthOf()` in `data-model.js` leitet daraus den Status ab (OK / Auffällig / Instabil: ≥ 3 Retransmits und ≥ 2 % der Datensegmente), `metricValue(…, 'problems')` die Metrik „Probleme“ für Matrix und Graph; der Filter „Auffällige Verbindungen“ (Facette Problem → `any`, `connection.problems > 0`; der Chip in der Filterleiste ist ein Schnellzugriff darauf) wird über `facetPredicate()` in `computeVisibleConnections()` angewendet (die Paare entstehen danach aus den sichtbaren Verbindungen), nicht aber im PCAP-Export-Worker. Für die Kachel „MTU und Fragmentierung“ liefert der Decoder pro Paket IP-Paketlänge, DF-Bit, Fragment-Kennzeichnung (IPv4-Flags/Offset bzw. IPv6-Fragment-Extension-Header; `isFirstFragment` zählt fragmentierte Datagramme), die TCP-MSS-Option aus SYN-Paketen sowie die in ICMP „Fragmentation needed“ / ICMPv6 „Packet Too Big“ gemeldete MTU. Die Pfad-MTU ist daraus nur abschätzbar (größtes IP-Paket als untere Schranke, MSS + 40 bzw. + 60 Byte als angekündigte MTU). **Layer 2, Apple, DNS-Server, Private Relay (1.8.0):** `decodeFrame()` klassifiziert alles, was weder IPv4/IPv6 noch ARP ist (802.3-Frames per LLC/SNAP, sonst per Ethertype), als `protocol: 'L2'` mit `l2 = { name, offset, length }` und liest bis zu zwei VLAN-Tags (`vlanId`). Der `Aggregator` ignoriert L2-Frames (ihre Multicast-Ziel-MACs sollen keine Geräte werden), `l2-parser.js` (`parseL2Details()`) liest BPDU, CDP-/LLDP-TLVs und LACPDU, `TrafficStats.addL2()` aggregiert (Root-Bridges je VLAN, Topologieänderungen, Nachbarn, LACP-Zustand). Die Namen der Nachbarn fließen über `Aggregator.addAnnouncedNames()` als Fallback-Beschriftung in die Geräte (IP-Geräte nur über die Management-IP, MAC-Geräte über die MAC – nie über die MAC eines IP-Geräts, die bei Routing der Router wäre). `classification.js` ist die einzige Stelle mit Listen (Resolver-Adressen je Anbieter, Apple-Namensregeln, Relay-Namensmuster, Apple-Netz 17.0.0.0/8, Umbrella-Blockseiten-Präfix 146.112.) plus den kleinen Matchern; Listen ändern, nicht die Funktionen, und `CLASSIFICATION_VERSION` anheben (steht in der Oberfläche). `parseDnsMessage()` liefert zusätzlich Typ und Antwort-Adressen/CNAMEs, `parseMdnsNames()` die Namen einer mDNS-Nachricht, `parseTlsHello()` das SNI. Private-Relay-Erkennung in `TrafficStats`: Abfragen werden per Muster (`mask*.icloud.com`, `mask*.apple-dns.net`) erkannt, die Antwort wird als NODATA/NXDOMAIN/Adressen/Blockseite/Fehler eingestuft, die Antwortzeit aus dem Abstand Anfrage–Antwort berechnet, Adressen aus „sauberen“ Antworten werden als Relay-Adressen gemerkt, späterer Verkehr auf Port 443 zu diesen Adressen und ClientHellos mit Relay-SNI zählen als Nutzung. Alles sind Heuristiken auf unverschlüsselten Metadaten; die Blockseiten-Erkennung über 146.112.0.0/16 stammt aus dem Betrieb, nicht aus der Cisco-Dokumentation.

**Top-Talker** werden nicht im Worker, sondern im Hauptthread aus den vorhandenen Paaren berechnet (`computeDeviceTraffic()`: `pair.aToB` wurde von `pair.a` gesendet und von `pair.b` empfangen, `bToA` umgekehrt). **TLS** (`tls-parser.js`, klassisches Worker-Skript): Der Worker prüft bei jedem TCP-Segment mit Nutzdaten (ohne Retransmits), ob der Payload mit einem TLS-Handshake-Record (Typ 22, Version 3.x) beginnt, und liest daraus bei ServerHello Version (Extension `supported_versions`, sonst Legacy-Feld) und Cipher Suite, bei ClientHello die höchste angebotene Version; GREASE-Werte werden ignoriert. Es gibt bewusst kein TCP-Reassembly – ServerHellos sind klein genug, bei einem ClientHello, dessen Extensions über mehrere Segmente laufen, fehlen Details. `stats-view.js` rendert HTML-Kacheln statt SVG (daher sind PNG-/SVG-Export auf diesem Tab deaktiviert). Wegen der CSP (`style-src 'self'`) sind Inline-`style`-Attribute auch in `innerHTML` blockiert: Breiten/Höhen/Farben werden als `data-*`-Attribute ausgegeben und nach dem Rendern per CSSOM (`element.style`) gesetzt, was die CSP erlaubt.

**Verbindungen als Tabelle** (`connections-table-view.js`): Alternative Darstellung desselben Verbindungen-Tabs (Umschalter Diagramm/Tabelle, `state.connectionsView`). Reines HTML; Sortierung, aufgeklappte Zeilen (`state.expandedConnectionIds`) und Filter liegen in `app.js`, die Tabelle meldet Klicks über `handlers` zurück und wird dann komplett neu gerendert (die Scroll-Position bleibt erhalten, da der scrollende `.view`-Container nicht ersetzt wird). Die Filter-Chips über der Tabelle und die der Seitenleiste lesen beide aus `state` (`syncSidebarFilterControls()`), bleiben also immer synchron. Die Listener werden per `container.onclick`/`onkeydown` zugewiesen (nicht hinzugefügt), damit wiederholtes Rendern keine doppelten Handler erzeugt.

**Zeitleiste** (`timeline-view.js`): viertes Tab, ein Gantt-Diagramm derselben Verbindungen (Geräte-Paar + Protokoll + Port). Anders als bei Matrix/Graph/Verbindungen ist hier nicht die Geräteliste die Zeilenachse, sondern jede Verbindung selbst eine Zeile mit einem waagerechten Balken von `firstSeen` bis `lastSeen`; Zeilen sind aufsteigend nach `firstSeen` sortiert (früheste Verbindung oben, späteste unten), statt nach Volumen wie im Verbindungen-Tab. Da eine einzelne Verbindung nur Anfang/Ende kennt (keine Einzelpaket-Zeitstempel dazwischen, siehe Backlog-Hinweis in [features.md](features.md#backlog-nicht-bestandteil-dieser-version)), ist der Balken eine reine Aktivitätsspanne, keine Aussage über die tatsächliche Paketverteilung innerhalb dieser Spanne. Sehr kurze (Einzelpaket-)Verbindungen erhalten eine Mindestbreite, damit sie sichtbar bleiben.

Der Zeitachsen-Bereich ist – anders als bei Graph/Verbindungen – **nicht** per Zoom-to-Fit-Transform auf eine Gruppe gelöst, sondern klassisch über eine `d3.scaleTime()`-Skala, die den gesamten Zeitraum von vornherein auf die Breite des Plot-Bereichs abbildet (das Darstellungsproblem bei Graph/Verbindungen – „natürliche" Diagrammgröße kann den Container weit überschreiten – existiert hier für die Zeitachse nicht, da die Skala den Zeitraum immer exakt auf die verfügbare Breite passt). `d3.zoom()` wird stattdessen für interaktives Hinein-/Herauszoomen und Verschieben entlang der Zeitachse verwendet: bei jedem Zoom-Event wird die Skala über `transform.rescaleX()` neu berechnet und sowohl die Achsen-Ticks als auch alle Balken-Positionen/-Breiten direkt neu gezeichnet (nicht per CSS-Transform auf eine Gruppe) – so bleiben Balkenhöhe und Beschriftungsgröße unabhängig vom Zoomfaktor lesbar. Die Geräte-/Verbindungs-Beschriftungsspalte links ist fix positioniert und nimmt am horizontalen Zoom/Pan nicht teil (per `<clipPath>` auf den Plot-Bereich begrenzt); vertikal scrollt das gesamte Diagramm bei vielen Zeilen normal über den Container, ohne eigenen Zoom. Wie beim Verbindungen-Tab werden höchstens `MAX_TIMELINE_RENDER` (300) Zeilen gezeichnet, mit Warnhinweis bei Überschreitung.

Jede Zeilenbeschriftung besteht aus Source-IP und „→ Destination-IP · Protokoll Port" (siehe nächster Abschnitt). Passt das komplett in eine Zeile (bis 36 Zeichen), wird ein einzeiliges `<text>` gerendert; darüber hinaus – vor allem bei IPv6-Adressen, die auch mit Hostname-Zusatz regelmäßig länger sind als IPv4 – wird die Beschriftung über zwei `<tspan>`-Zeilen (Source-IP oben, Rest darunter) verteilt statt sie mit „…" abzuschneiden. `ROW_HEIGHT` ist entsprechend groß genug für beide Fälle bemessen.

### Initiator-Richtung, Source/Destination-Terminologie in Tooltips und Kacheln

`pair.a`/`pair.b` bzw. `connection.a`/`connection.b` werden in `parser.worker.js` immer vom **ersten** Paket gesetzt, das dieses Paar/diese Connection anlegt – `a` ist also stets das Gerät, das die Kommunikation zuerst initiiert hat. Tooltips und angeheftete Kacheln (`pairDetailsHtml()`/`connectionDetailsHtml()` in `app.js`) nutzen das aus, um immer „Source IP → Destination IP" mit genau einem Pfeil anzuzeigen (statt eines richtungslosen „↔") – unabhängig davon, in welcher Zeilen-/Spaltenreihenfolge z. B. eine Matrixzelle gehovert wurde: `pairDetailsHtml()` löst Source/Destination stets über `pair.a`/`pair.b` und `state.deviceIndex` auf, nicht über die von der jeweiligen Ansicht übergebenen Geräte.

Ein **Geräte-Paar** aggregiert Datenverkehr in beide Richtungen – ein einzelnes, paketweise wechselndes „Source-Port"/„Destination-Port"-Paar ist auf dieser Ebene nicht sinnvoll definierbar. Statt eines einzigen, richtungsunabhängig vermischten `ports`-Sets hält `parser.worker.js` deshalb pro Paar zwei getrennte Sets: `portsA` (alle Ports, die das Source-Gerät jemals genutzt hat, unabhängig von Sende-/Empfangsrichtung) und `portsB` (entsprechend für das Destination-Gerät). Tooltips/Kacheln zeigen dies als „Source Port" / „Destination Port".

Eine einzelne **Connection** (Geräte-Paar + Protokoll + Service-Port) repräsentiert dagegen einen weitgehend richtungsstabilen Fluss, da die Service-Port-Gruppierung ohnehin beide Richtungen zusammenführt. Hier ist ein echtes „Source-Port/Destination-Port"-Paar sinnvoll und wird direkt vom ersten Paket übernommen, das diese Connection eröffnet hat (`connection.srcPort`/`connection.dstPort` in `parser.worker.js`, zusätzlich zum gruppierenden `connection.port`).

Für den Excel-Rohdaten-Export reicht die reine Paar-Aggregation nicht aus, da `portsA`/`portsB` Ports über alle Protokolle hinweg vermischen (TCP- und UDP-Ports eines Paares wären sonst nicht unterscheidbar). `derivePairs()` bildet deshalb zusätzlich pro Paar eine Aufspaltung je Protokoll (`pair.protocolBreakdown`) mit denselben Feldern (`packets`, `bytes`, `portsA`, `portsB`, `firstSeen`, `lastSeen`) getrennt je Protokoll, wodurch `export-excel.js` eine dedizierte Zeile pro (Paar, Protokoll)-Kombination statt einer Zeile pro Paar erzeugen kann.

### Angeheftete Auswahl (persistente Detail-Kacheln)

Klick auf eine Matrixzelle, eine Graph-Kante/einen Graph-Knoten, einen Verbindungen-Pfeil oder einen Zeitleiste-Balken heftet dieselben Informationen, die der Hover-Tooltip zeigen würde, dauerhaft als Kachel im rechten Panel an (`state.pinnedItems` in `app.js`). Die HTML-Bausteine (`pairDetailsHtml()`, `connectionDetailsHtml()`, `deviceDetailsHtml()`) sind bewusst von den Tooltip-Aufrufen getrennt und werden von beiden – transientem Tooltip und persistenter Kachel – gemeinsam genutzt, um Duplikation zu vermeiden. Jede Kachel hat eine stabile ID (`pair:…`, `connection:…`, `device:…|` jeweils basierend auf `pairKey()`/Geräte-ID), wodurch erneutes Klicken desselben Elements keine doppelte Kachel erzeugt. Kacheln werden nur explizit über ihr „×" oder „Alle entfernen" geschlossen, nie automatisch (auch nicht bei Filter-/Tab-Wechsel) – einzig ein neuer Datei-Import setzt die Auswahl zurück, da sich die zugrunde liegenden Objekte dann ändern.

Der Export-Menüpunkt „Nur angeheftete Auswahl (.xlsx)" (deaktiviert, solange keine Kachel angeheftet ist) exportiert ausschließlich die aktuell angehefteten Elemente als eigenes Sheet „Auswahl" (`exportSelectionToExcel()` in `export-excel.js`), mit einheitlichen Spalten über alle drei Kachel-Typen hinweg (Typ, Source IP/Destination IP, Protokoll, Source Port/Destination Port, Pakete, Bytes, Zeitraum) – unabhängig von der aktuellen Tab-/Filteransicht. Angeheftete Geräte-Paare werden dabei wie im Haupt-Rohdaten-Sheet über `pair.protocolBreakdown` in eine Zeile je Protokoll aufgespalten.

### Geräteliste: angeheftete Auswahl und automatische Nachbarschaftsauswahl

Die Geräteliste im Seitenpanel (`renderDeviceList()` in `app.js`) ist in zwei Gruppen geteilt, jeweils aufsteigend nach Adresse sortiert (`compareDevicesByAddress`): ausgewählte Geräte oben (optisch abgesetzt durch Hintergrundfarbe und eine Trennlinie), alle übrigen darunter. Wird eine Checkbox deaktiviert, verschwindet das Gerät aus der oberen Gruppe und erscheint einsortiert in der unteren.

Ist die Auswahl leer (`state.selectedIds.size === 0`) und wird ein einzelnes Gerät angehakt, werden zusätzlich automatisch alle Geräte ausgewählt, mit denen dieses Gerät mindestens einmal kommuniziert hat (`relatedDeviceIds()` in `data-model.js`, direkte Nachbarschaft über die Paar-Liste, nicht transitiv). So zeigt die Matrix sofort einen sinnvollen Ausschnitt statt eines isolierten Einzelgeräts. Die automatisch mit ausgewählten Geräte sind danach normale, unabhängig abwählbare Checkboxen – die Kaskade greift nur beim Übergang von „keine Auswahl" zu „eine Auswahl", nicht bei weiteren Klicks auf eine bereits nicht-leere Auswahl.

### Port-Filter: zweiter Seitenpanel-Reiter

Neben „Geräte" listet ein zweiter Reiter „Ports" (`setSidebarTab()` in `app.js`) jede im Capture tatsächlich genutzte (Protokoll, Service-Port)-Kombination auf. `computePortEntries()` in `data-model.js` gruppiert dafür `state.connections` nach `${protocolGroupOf(protocol)}|${port}` (nur TCP/UDP – ICMP/ARP haben keinen Port und werden übersprungen) und sammelt je Gruppe alle beteiligten Geräte-IDs sowie Paket-/Byte-Summen; das Ergebnis ist bereits numerisch nach Port aufsteigend sortiert. `WELL_KNOWN_PORTS`/`wellKnownPortName()`/`portListLabel()` (ebenfalls `data-model.js`) bilden eine kleine, nicht erschöpfende Tabelle gängiger IANA-Portnummern auf lesbare Namen ab (z. B. „22 (SSH)"); unbekannte Ports erscheinen ohne Klammerzusatz statt geraten oder ausgeblendet zu werden. Da ein Port sowohl über TCP als auch UDP vorkommen kann, ist jede Zeile explizit einem Protokoll zugeordnet (Label z. B. „53 (DNS) · UDP").

Die Portliste teilt sich bewusst Suchfeld (`#device-search`) und TCP/UDP-Protokoll-Chips (`#protocol-filters`) mit der Geräteliste, statt eigene Steuerelemente zu bekommen – beide Eingabe-Handler rufen zusätzlich `renderPortList()` auf. Die „Alle“-Checkbox (`#select-all`) wirkt in beiden Reitern auf die Geräteauswahl; Multicast/Broadcast und „Nur Probleme“ sitzen in der Filterleiste und gelten für alle Ansichten.

Ein Häkchen bei einem Port-Eintrag fügt alle in `entry.deviceIds` gesammelten Geräte-IDs zu `state.selectedIds` hinzu (Vereinigung mit einer eventuell bereits bestehenden Auswahl); Entfernen des Häkchens entfernt exakt dieselben IDs wieder – ohne Herkunfts-Tracking, d. h. ein Gerät, das über zwei sich überschneidende Ports ausgewählt wurde, verschwindet bereits beim Abwählen des ersten davon. Der Checkbox-Zustand selbst ist rein abgeleitet (`isPortEntryFullySelected()`: alle beteiligten Geräte aktuell in `state.selectedIds`), keine eigene persistente Auswahl – so bleiben Geräte- und Portliste immer konsistent zum selben `state.selectedIds`, unabhängig davon, über welchen Reiter zuletzt selektiert wurde. Das erlaubt z. B., mit einem Klick auf „22 (SSH)" die komplette SSH-Kommunikation in allen vier Ansichten sichtbar zu machen, ohne die beteiligten IPs vorher kennen zu müssen.

## Filter-Facetten, abgeleitete Paare und Tests (2.1.0)

**Eine Quelle für alle Ansichten.** Die einzige Datengrundlage aus dem Worker sind die *Verbindungen* (Geräte-Paar + Protokoll + Service-Port). `computeVisibleConnections()` (`data-model.js`) wendet Seitenleisten-Auswahl (beide Endpunkte ausgewählt), Protokoll-Chips, „Multicast/Broadcast ausblenden“ und die Facetten (darunter „Auffällig“) an; Verbindungen-Tab, Zeitleiste und Tabelle zeigen genau diese Liste, Matrix, Graph und Excel-Export zeigen `derivePairs(sichtbare Verbindungen)`. Dadurch passen Zahlen und Filter überall zusammen – ein Protokoll-Chip verkleinert jetzt auch die Paket-Summen eines Paares in der Matrix, statt nur Paare auszublenden, und „Multicast/Broadcast ausblenden“ blendet nur die betroffenen Verbindungen aus statt jedes Paares, das irgendwann ein Multicast-Paket hatte.

**`derivePairs()`** summiert pro Geräte-Paar die Verbindungen: Summen, Richtungs-Summen (`aToB`/`bToA` = was `pair.a` bzw. `pair.b` gesendet hat), Ports je Gerät, Aufspaltung je Protokoll (`protocolBreakdown`), TCP-Summary ohne Einzelereignis-Zeitstempel. `pair.a`/`pair.b` sind der Absender der Verbindung mit dem frühesten `firstSeen`. Dafür tragen Verbindungen jetzt `key` (Paar|Protokoll|Service-Port), vollständige Port-Mengen je Richtung (`srcPorts`/`dstPorts`) und `facets`. Abgesichert ist das durch Golden-Dateien (`tests/golden/`), die aus der früheren Paar-Aggregation des Workers erzeugt wurden, und eine einmalige Prüfung gegen echte Captures.

**Facetten** (`filters.js`): Kriterien auf dem Inhalt einer Verbindung – Port, Problem, TLS-Version, Cipher Suite, ICMP-Typ, DNS-Antwortcode, DNS-Anbieter, Private-Relay-Zustand, Apple-Dienst, Fragmentierung. Der Worker sammelt sie pro Paket als `hints` (`TrafficStats.add/addTls/addDns` füllen sie, `Aggregator.addPacket()` speichert sie in `connection.facets`, lazy – die meisten Verbindungen haben keine). Aktive Facetten sind eine `Map(Dimension → Set(Werte))`: Werte einer Dimension = ODER, verschiedene Dimensionen = UND (`connectionMatchesFacets()`). Die Oberfläche zeigt sie als entfernbare Chips in der Filterleiste („Weitere Filter“, `.chip.removable`), das Menü „+ Filter“ listet je Dimension die im Capture vorkommenden Werte mit Anzahl (`collectFacetOptions()`), „Alle zurücksetzen“ stellt auch Protokoll-Chips und die beiden Schalter zurück. Neue Dimension = ein Eintrag in `FACET_DIMENSIONS` plus der Hint im Worker.

**Statistik nach Auswahl (Phase 2).** Der Worker behält die Capture-Datei nach dem Parsen (`retainedBuffer`, bis `MAX_RETAINED_BYTES` = 1 GiB – beim Einlesen lag sie ohnehin komplett im Speicher, sie wird nur länger gehalten; die Ergebnisnachricht meldet `scopeAvailable`). Auf `{ type: 'scope', requestId, keys }` antwortet er mit `scopedStats`: `computeScopedStats()` parst die Datei erneut, dekodiert jedes Paket, nimmt nur die, deren `connectionKeyOf()` in `keys` liegt (der Schlüssel, unter dem der Aggregator das Paket ablegt, dieselbe Funktion), und lässt sie durch `analysePacket()` laufen – dieselbe Funktion, die auch der erste Durchlauf nutzt, sodass beide für dieselben Pakete identische Zahlen liefern (getestet: Scope „alle“ = Gesamtdurchlauf). Layer-2-Frames, Frames ohne Adressen und Self-Talk haben keinen Schlüssel und sind nie Teil eines Scopes. Alle 5000 Pakete gibt der Worker per `setTimeout` die Kontrolle ab; hat der Seitenthread inzwischen eine neuere Anfrage geschickt (`latestScopeRequest`), bricht die ältere ab und antwortet nicht. Im Seitenthread (`renderStatsTab()` in `app.js`) ist der Scope die Liste der sichtbaren Verbindungen *ohne* den IPv4/IPv6-Umschalter; entspricht sie allen Verbindungen, werden die Zahlen des ersten Durchlaufs genutzt, sonst wird per Fingerabdruck der Verbindungsliste (`scopeSignature()`: Anzahl + FNV-1a über die Schlüssel) im Cache (`state.scopeCache`, 8 Einträge) nachgesehen oder angefragt; solange die Antwort aussteht, bleibt die alte Anzeige abgedunkelt (`.is-loading`, nach 150 ms) stehen. Ist die Datei zu groß (`scopeAvailable` false), zeigt die Statistik den gesamten Capture mit Hinweis. Die Layer-2-Kachel bekommt immer die Gesamtwerte.

**Klick-Filter aus der Statistik (Phase 4).** Zeilen in `stats-view.js` tragen eine Aktion (`actionAttrs()`): `{ facet: [Dimension, Wert] }` schaltet die Facette um, `{ devices: [a, b?] }` setzt die Geräteauswahl. Sie werden als `.stats-row.is-action` (`role="button"`, `tabindex="0"`, bei Facetten `aria-pressed`) gerendert; `app.js` hört per Delegation am Statistik-Container auf Klick und Enter/Leertaste (`activateStatsRow()`; nach Tastaturbedienung gibt `restoreStatsFocus()` der neu gezeichneten Zeile den Fokus zurück). Die Werte der Zeilen entsprechen den Facettenwerten aus `filters.js` (z. B. Port `TCP|443`, ICMP `Protokoll|Typ|Code`, DNS-Code als Zahl, Anbieter- und Apple-Gruppennamen). Ein Top-Talker-Gerät wählt es samt `relatedDeviceIds()` aus (wie eine neue Auswahl in der Seitenleiste), ein Paar genau die zwei Geräte.

Damit eine Karte nach dem Klick weiter alle Werte ihrer Dimension zeigt, bekommt sie die Statistik *ohne den Filter der eigenen Dimension*: `getExtraScopes()` bildet je aktiver Dimension (`STATS_FACET_DIMENSIONS`) die Verbindungsliste mit `facetsWithout()`, sofern sie sich von der Hauptliste unterscheidet; die Anfrage `{ type: 'scope', requestId, keys, extras: { Dimension: keys } }` lässt den Worker alle Mengen in **einem** Durchlauf über die Datei auswerten (ein `TrafficStats` je Menge, Antwort `stats` + `extras`). Der Cache-Schlüssel setzt sich aus Haupt- und Zusatz-Fingerabdrücken zusammen, Einträge sind `{ stats, extras }`. `renderStats()` nimmt `extras` und `facets` entgegen: Karten für Problem, ICMP, Port, TLS-Version/-Cipher, DNS-Antwortcode, DNS-Anbieter, Relay-Antworten und Apple-Dienste lesen ihre Listen aus `extras[Dimension]`, sonst aus der Hauptstatistik; Zusammenfassungen und alle übrigen Karten bleiben bei der Hauptstatistik.

**Tests** (`tests/`, `node tests/run.js`, keine Abhängigkeiten): `tests/lib/pcap-builder.js` erzeugt synthetische Captures per Skript (Ethernet/VLAN, ARP, IPv4, UDP, TCP mit Sequenznummern, ICMP, DNS, TLS-Hellos, STP/CDP/LLDP/LACP) – bewusst keine echten Captures im öffentlichen Repository; `tests/lib/run-worker.js` führt den echten `parser.worker.js` samt `importScripts()` in einem Node-`vm` aus. Geprüft werden die Analysen (`stats.test.js`), die abgeleiteten Paare (`pairs.test.js`), Facetten/Sichtbarkeit (`filters.test.js`) und die Statistik nach Auswahl samt Abbruch älterer Anfragen (`scope.test.js`; `createWorkerSession()` in `tests/lib/run-worker.js` bildet die Nachrichten der Seite nach).

Seit 2.0.0 baut die Oberfläche auf einem gemeinsamen Design System auf (Material-Design-3-Grundlage, Theme „Neutral“ in Stahlblau, ohne Marken-Assets). Es wird nicht von Hand kopiert, sondern per Sync-Skript des Design Systems eingespielt (`sync-design.sh --theme neutral`) und liegt in:

Alles PacketAtlas-Eigene steht in `css/app.css` und nutzt ausschließlich die Tokens: Layout (Fensterfläche ohne Seiten-Scrollen, `.app-shell.fill`), die SVG-Ansichten, Statistik, Verbindungstabelle, Tooltip, angeheftete Kacheln. Problemfarben sind dort zentral als `--pa-ok`/`--pa-warn`/`--pa-bad` abgeleitet; die Matrix mischt ihre Farbskala per `color-mix()` aus `--md-primary` bzw. `--pa-bad` mit der Oberfläche, sodass sie dem Hell/Dunkel-Modus folgt.

## Web Worker

`parser.worker.js` kapselt den gesamten rechenintensiven Teil (Parsing + Decoding + Aggregation) und kommuniziert über `postMessage`:

- `progress`-Nachrichten (Anteil verarbeiteter Bytes) für die Fortschrittsanzeige.
- Eine abschließende `result`-Nachricht mit dem vollständig aggregierten Datenmodell (Devices + Connections + Statistik).
- Eine `error`-Nachricht bei nicht behebbaren Parsing-Fehlern.

**Cache-Busting:** `parser.worker.js` selbst sowie die per `importScripts()` nachgeladenen Dateien (`pcap-parser.js`, `pcapng-parser.js`, `packet-decoder.js`, `dns-resolver.js`, `traffic-stats.js`, `tls-parser.js`, `l2-parser.js`, `classification.js`) sind klassische Skript-Requests, die der Browser unabhängig vom Haupt-Dokument im HTTP-Cache halten kann – ein Seiten-Reload (auch ein harter) garantiert in manchen Browsern nicht, dass nach einem Update tatsächlich neuer Worker-Code läuft. `app.js` instanziiert den Worker deshalb als `new Worker(\`parser.worker.js?v=${APP_VERSION}\`)`.

Die Version wird mit **`./bump-version.sh <x.y.z>`** an allen nötigen Stellen gesetzt – im Alltag übernimmt das der Git-Hook `.githooks/pre-commit` (Aktivierung einmalig pro Clone: `git config core.hooksPath .githooks`): Man ändert nur `APP_VERSION` in `app.js`, beim Commit zieht der Hook alle `?v=`-Strings nach und stellt die geänderten Dateien automatisch in den Commit. Das Skript setzt: `APP_VERSION` in `app.js`, jeder statische ES-Import (`from './x.js?v=<x.y.z>'`) in den Top-Level-`.js`-Dateien sowie `style.css` und `app.js` im `index.html`. Hintergrund: Browser cachen jedes ES-Modul einzeln, GitHub Pages liefert `Cache-Control: max-age=600` – ohne Version im Modul-URL konnte nach einem Update kurzzeitig eine neue `app.js` gegen eine alte, gecachte `data-model.js` laufen („does not provide an export named …“). Mit identischen `?v=`-Query-Strings an allen Modul-URLs (wichtig: überall derselbe String, sonst entstünden zwei Modul-Instanzen) schaltet der komplette Dateisatz gemeinsam um. Statische `import`-Anweisungen lassen sich nicht aus einer Konstante zusammensetzen, und die CSP (`script-src 'self'`) verbietet Inline-Skripte und damit Import-Maps – deshalb Klartext im Quelltext plus Skript. `parser.worker.js` und `pcap-export.worker.js` lesen ihre Version weiterhin zur Laufzeit aus dem `?v=` ihrer eigenen Worker-URL (`new URL(self.location.href).searchParams.get('v')`), die `app.js` aus `APP_VERSION` zusammensetzt. Der Footer-Text in `index.html` wird von `app.js` beim Laden aus `APP_VERSION` in ein leeres `<span id="app-version">` geschrieben. Nur `releases.md` (der geschriebene Changelog) bleibt manuell zu pflegen.

Der Main-Thread bleibt während des Parsens vollständig responsiv.

### Klassischer Worker statt Modul-Worker

`parser.worker.js` wird bewusst als **klassischer Worker** (`new Worker('parser.worker.js')`, ohne `{ type: 'module' }`) erzeugt und lädt `pcap-parser.js`, `pcapng-parser.js`, `packet-decoder.js`, `dns-resolver.js`, `traffic-stats.js`, `tls-parser.js`, `l2-parser.js` und `classification.js` per `importScripts()` nach – nicht über ES-`import`. Modul-Worker sind eine vergleichsweise junge Web-Plattform-Funktion (Firefox unterstützt sie erst seit Version 114, Mitte 2023) und schlagen in nicht unterstützten Browsern mit einer kryptischen, inhaltsunabhängigen Fehlermeldung fehl. `importScripts()` wird dagegen seit weit über einem Jahrzehnt von allen Browsern unterstützt. Da klassische Scripts (anders als Module) keinen eigenen Datei-Scope haben, teilen sich alle per `importScripts()` geladenen Dateien denselben globalen Scope wie `parser.worker.js` – die Funktionen aus den vier Parser-Dateien sind dort daher ohne Import direkt als globale Bezeichner nutzbar. Der `Aggregator` (Geräte-/Paar-Aggregation) ist deshalb direkt in `parser.worker.js` definiert statt in `data-model.js`, das als ES-Modul weiterhin ausschließlich vom Main-Thread (`app.js` und die Views) importiert wird.

## PCAP-Export (gefilterte Re-Exportierung)

Der Export-Menüpunkt „Als PCAP (gefiltert) …" erzeugt eine neue, klassische `.pcap`-Datei mit den Paketen der aktuell sichtbaren Verbindungen – optional mit oder ohne Payload.

### Umfang: dieselben Verbindungen wie die Statistik

Der Export nimmt `getScopeConnections()` – die Verbindungen, die Geräteauswahl, Protokoll-Chips, „Multicast/Broadcast ausblenden“ und alle Filter (Facetten, inkl. „Auffällig“) passieren; der Adressfamilien-Umschalter gilt nicht. Das ist dieselbe Liste wie für die Statistik nach Auswahl (siehe dort), so zeigen Statistik, Ansichten und Export dieselben Daten. Übergeben werden nur die Verbindungsschlüssel (`connection.key`, siehe `connectionKeyOf()`) und der `payloadMode` (`'full'` / `'headers-only'`) – als Arrays/Primitives, keine Sets/Maps über `postMessage`. Der Dialog zeigt vorab Paket- und Verbindungsanzahl (`currentExportScope()`) und sperrt „Exportieren“ bei leerem Scope.

Ein Paket gehört zum Export, wenn sein Verbindungsschlüssel in der Liste steht. Layer-2-Steuerframes (STP, CDP, LLDP …), Frames ohne Adressen und Eigenverkehr haben keinen Schlüssel und sind nie enthalten (wie schon vor der Umstellung). Vor 2.1.0 filterte der Export je Paket nach Auswahl, Protokollgruppe und Multicast-Schalter und kannte weder „Auffällig“ noch die Facetten; die Verbindungsebene ist dasselbe Ergebnis für die alten Filter und erweitert sie um die neuen.

### Woher die Bytes kommen

Der Parse-Worker behält die Capture nach dem Parsen (`retainedBuffer`, bis `MAX_RETAINED_BYTES` = 1 GiB, siehe „Statistik nach Auswahl“) und beantwortet `{type:'export', requestId, keys, payloadMode}` mit `exportProgress` / `exportResult` (`buffer`, `packetCount`, `skippedLinkTypeCount`) / `exportError`. Der Aufbau läuft in einem Zug (`exportScope()`); ein Abbruch im Dialog verwirft nur das Ergebnis (`state.activeExportId`), der Worker rechnet zu Ende. Den eigentlichen Aufbau übernimmt `buildFilteredPcap()` aus `capture-scope.js` – ein klassisches Skript, das Parse-Worker und Fallback-Worker per `importScripts()` laden und das auch `connectionKeyOf()` und `parseFrames()` enthält, damit Statistik, Aggregation und Export Pakete nach exakt demselben Schlüssel zuordnen.

### Fallback für Captures über 1 GiB

Ist die Capture zu groß für den Speicher des Workers (`scopeAvailable === false`), bleibt der frühere Weg: Der Dialog fragt nach der Original-Datei. `app.js` berechnet beim Import einen SHA-256-Hash (`sha256Hex()`, native `crypto.subtle.digest()`) und vergleicht ihn beim Re-Upload; bei Übereinstimmung wird der Buffer für die Session gecacht (`state.originalFileBuffer`), ein neuer Import verwirft ihn (`startParsing()`). Der Hash dient nur der Fehlervermeidung (falsche Datei), nicht der Manipulationssicherheit. Der Export läuft dann in `pcap-export.worker.js` (lädt Parser, Decoder und `capture-scope.js`) mit `{ buffer, keys, payloadMode }`.

### Payload-Kürzung

Bei `payloadMode === 'headers-only'` wird jedes passende Frame auf `decoded.headerEndOffset` gekürzt – ein neues Feld, das `packet-decoder.js`/`applyL4()` pro Paket berechnet: für TCP das Ende des Headers inklusive Optionen (Data-Offset-Feld, Byte 12 des TCP-Headers), für UDP/ICMP/ICMPv6 die festen 8 Byte Header, für ARP `null` (keine Kürzung – ARP hat keinen nennenswerten Payload-Begriff), für unbekannte L4-Protokolle das Ende des L3-Headers. Die Kürzung wird zusätzlich beim tatsächlichen Schreiben auf die tatsächliche Frame-Grenze geclamped, falls `headerEndOffset` durch eine snaplen-verkürzte Originaldatei über das verfügbare Frame-Ende hinausragen sollte.

Geschrieben wird nach dem klassischen Snaplen-Prinzip: `incl_len` (in der Ausgabedatei tatsächlich gespeicherte Länge) wird gekürzt, `orig_len` bleibt die tatsächliche ursprüngliche Framegröße – exakt das, was `tcpdump -s <n>`/`editcap -s <n>` heute schon tun, kein Sonderformat. Wireshark zeigt gekürzte Frames entsprechend als „[Packet size limited during capture]" an, mit weiterhin korrekter Paket-/Byte-Statistik.

### Ausgabeformat

Geschrieben wird immer **klassisches pcap** (24-Byte-Global-Header + 16-Byte-Record-Header je Paket), nicht pcapng – einfacher zu schreiben, von jedem Tool lesbar, deckt den Normalfall (eine Schnittstelle, ein Link-Type) vollständig ab. Da klassisches pcap nur einen einzigen Link-Type pro Datei kennt, eine pcapng-Quelle aber theoretisch mehrere Interfaces mit unterschiedlichen Link-Types mischen könnte, wird der **häufigste** Link-Type unter den passenden Paketen ermittelt und nur dieser übernommen; abweichende Pakete werden ausgelassen und die Anzahl dem Nutzer nach Abschluss als Warnhinweis gemeldet (`skippedLinkTypeCount`).

### Ablauf im Dialog

`app.js` verwaltet den Dialog (`#pcap-export-overlay`) über `openPcapExportDialog()`/`closePcapExportDialog()`. Der Einleitungstext nennt Paket- und Verbindungsanzahl (`exportScopeSummary()`). Normalfall: Payload-Wahl und „Exportieren“-Button, ein Klick startet den Aufbau im Parse-Worker. Fallback: ohne verifizierten Buffer die Dropzone, `handlePcapReupload()` verifiziert die Datei per Hash-Vergleich und startet bei Erfolg automatisch den Export; mit gecachtem Buffer entfällt die Dropzone. Fortschritt und Erfolg erscheinen als Schritte (`#pcap-step-hash` nur im Fallback, `#pcap-step-build`; je ein Fortschrittsbalken mit Label, der bei Abschluss über `completePcapStep()` grün wird und ein Häkchen bekommt, analog `resetPcapStep()` beim erneuten Öffnen). Nach dem Aufbau zeigt `showPcapExportSuccess()` die grüne Erfolgsmeldung (`#pcap-export-success`, inkl. Hinweis auf ausgelassene Pakete bei abweichendem Link-Type) und beschriftet „Abbrechen“ in „Schließen“ um – der Dialog schließt sich nicht automatisch, damit ein erfolgreicher Export nicht wie ein abgebrochener wirkt. Fehler (`exportError` bzw. `error`, z. B. „keine Pakete entsprechen der Filterung“, oder Hash-Mismatch) zeigt `showPcapExportError()` und setzt den Dialog über `showPcapAwaitingInput()` in den passenden Eingabezustand zurück, sodass sofort ein neuer Versuch möglich ist.

## Sicherheit / Datenschutz

- Content-Security-Policy (Meta-Tag in `index.html`) unterbindet jede externe Verbindung: `default-src 'none'` mit gezielten Ausnahmen nur für `'self'` (Skripte, Styles, Fonts, Worker) sowie `data:`/`blob:` bei Bildern (letzteres ausschließlich für den clientseitigen PNG-Export benötigt – eine reine In-Memory-Referenz auf zuvor selbst erzeugte Daten, keine Netzwerkverbindung).
- Keine CDN-Referenzen; alle Bibliotheken liegen lokal in `vendor/`, Icons als Inline-SVG-Sprite in `index.html`, Schrift ist die Systemschrift.
- Keine Analytics-/Tracking-Skripte.
- Datei-Inhalt verlässt zu keinem Zeitpunkt den Browser-Kontext (kein `fetch`, kein `XMLHttpRequest` im gesamten Code; `connect-src 'none'` erzwingt dies zusätzlich technisch).
